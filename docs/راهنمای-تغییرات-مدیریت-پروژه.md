# راهنمای تغییرات مدیریت پروژه و وظایف

## هدف تغییرات

به بک‌اند Karnex یک ماژول مدیریت پروژه اضافه شده است تا فرانت‌اند بتواند داده‌های واقعی پروژه، اسپرینت و وظیفه را دریافت و مدیریت کند. داشبورد فرانت نیز برای دریافت آمار و داده‌های اصلی از API به‌روزرسانی شده است.

## معماری

پیاده‌سازی مطابق ساختار موجود پروژه انجام شده است:

```text
Web (Controller) → MediatR → Application/Features → IUnitOfWork → Infrastructure/EF Core → SQL Server
```

- کنترلرها فقط درخواست را دریافت و با `Mediator.Send` به Feature مربوط می‌فرستند.
- منطق کسب‌وکار، واکشی داده و ذخیره‌سازی در `Application/Features` قرار دارد.
- مدل‌های دامنه در `Domain` و نگاشت EF Core در `Infrastructure` هستند.
- DTOهای خروجی API در `Application/Dtos/ProjectManagement` قرار دارند.

## مدل‌های اضافه‌شده

### Project

نماینده یک پروژه است.

فیلدهای مهم: `Key`، `Name`، `Description`، `Type`، `Status`، `Privacy`، `Icon`، `Color`، `StartDate` و `EndDate`.

- `Key` در کل سیستم یکتا است.
- `Progress` در خروجی API محاسبه می‌شود و در دیتابیس ذخیره نمی‌شود.
- پیشرفت از نسبت وظایف تکمیل‌شده به کل وظایف پروژه محاسبه می‌شود.

### ProjectMember

رابط عضویت کاربر در پروژه است و شامل `ProjectId`، `UserId` و `Role` است. ترکیب `ProjectId` و `UserId` یکتا است.

### Sprint

اسپرینت وابسته به پروژه است و شامل نام، هدف، وضعیت، تاریخ شروع و پایان است.

وضعیت‌ها:

- `planned`
- `active`
- `completed`

### WorkItem

مدل اصلی وظیفه است. نام فنی آن `WorkItem` انتخاب شده تا با `System.Threading.Tasks.Task` تداخل نداشته باشد.

نوع وظیفه:

- `epic`
- `story`
- `task`
- `bug`
- `subtask`

وضعیت وظیفه:

- `todo`
- `inprogress`
- `review`
- `done`

اولویت وظیفه:

- `lowest`
- `low`
- `medium`
- `high`
- `highest`

هر WorkItem به یک پروژه متصل است و می‌تواند به اسپرینت، وظیفه والد، مسئول و گزارش‌دهنده متصل شود.

### WorkItemLabel، WorkItemComment و WorkItemAttachment

- Label: برچسب نام‌دار با رنگ اختیاری.
- Comment: متن نظر و شناسه نویسنده.
- Attachment: فقط اطلاعات فایل شامل نام، URL، نوع محتوا و حجم را نگه می‌دارد. آپلود فیزیکی فایل در این مرحله پیاده‌سازی نشده است.

## APIها

آدرس پایه در اجرای محلی:

```text
http://localhost:21547
```

### وظایف

| متد | مسیر | کاربرد |
| --- | --- | --- |
| GET | `/api/tasks` | دریافت فهرست وظایف |
| GET | `/api/tasks/{id}` | دریافت جزئیات یک وظیفه |
| POST | `/api/tasks` | ایجاد وظیفه |
| PUT | `/api/tasks/{id}` | ویرایش وظیفه |
| PATCH | `/api/tasks/{id}/status` | تغییر وضعیت وظیفه |
| DELETE | `/api/tasks/{id}` | حذف نرم وظیفه |
| POST | `/api/tasks/{id}/comments` | افزودن نظر |
| POST | `/api/tasks/{id}/attachments` | افزودن متادیتای فایل |
| GET | `/api/tasks/dashboard-stats` | آمار کارت‌های داشبورد |

فیلترهای قابل استفاده برای `GET /api/tasks`:

```text
?projectId=1&sprintId=2&status=inprogress&priority=high&assigneeId=user-id&search=login
```

نمونه ایجاد وظیفه:

```json
{
  "projectId": 1,
  "title": "اتصال فرم ورود به API",
  "description": "پیاده‌سازی ارتباط فرم با سرویس احراز هویت",
  "type": "task",
  "priority": "high",
  "assigneeId": "user-id",
  "reporterId": "user-id",
  "sprintId": 1,
  "parentId": null,
  "storyPoints": 5,
  "dueDate": "2026-10-01T00:00:00Z",
  "labels": [
    { "name": "API", "color": "#3b82f6" }
  ]
}
```

نمونه تغییر وضعیت:

```json
{ "status": "done" }
```

نمونه افزودن نظر:

```json
{
  "authorId": "user-id",
  "content": "پیاده‌سازی بررسی شد."
}
```

## پاسخ‌های مهم API

خروجی وظیفه شامل فیلدهایی مانند `id`، `key`، `title`، `status`، `priority`، `projectId`، `sprintId`، `labels`، `comments`، `attachments`، `subtasks` و `completedSubtasks` است.

خروجی آمار داشبورد:

```json
{
  "totalTasks": 25,
  "inProgressTasks": 8,
  "completedTasks": 10,
  "overdueTasks": 2
}
```

## دیتابیس و Migration

Migration زیر برای ایجاد جداول جدید ساخته شده است:

```text
20260923132254_AddProjectManagement
```

برنامه در زمان اجرا `Database.MigrateAsync()` را فراخوانی می‌کند؛ بنابراین با اجرای بک‌اند، migrationهای اعمال‌نشده به‌صورت خودکار اجرا می‌شوند.

برای اعمال دستی migration نیز می‌توان از دستور زیر استفاده کرد:

```powershell
dotnet-ef database update --project src\Infrastructure\Infrastructure.csproj --startup-project src\Web\Web.csproj --context ApplicationDbContext
```

## تغییرات فرانت‌اند داشبورد

فایل جدید `frontend/src/lib/karnex-api.ts` یک client ساده مبتنی بر `fetch` دارد. این client هم‌زمان APIهای آمار، وظایف، پروژه‌ها و اسپرینت‌ها را دریافت می‌کند.

در `DashboardPage.tsx` داده‌های زیر از API خوانده می‌شوند:

- کارت‌های آماری وظایف
- لیست وظایف داشبورد و فیلتر همه/باز/انجام‌شده
- توزیع پروژه‌ها بر اساس تعداد وظایف
- پروژه‌های فعال و میزان پیشرفت آن‌ها
- اسپرینت‌های فعال و پیشرفت آن‌ها

در صورت در دسترس نبودن API، صفحه بدون crash باقی می‌ماند و بخش‌های APIمحور خالی نمایش داده می‌شوند.

فعالیت‌ها، جلسات، یادآورها و آواتار اعضا هنوز از `mockData.ts` استفاده می‌کنند، چون برای آن‌ها API ساخته نشده است.

## پیکربندی فرانت‌اند

در صورت تفاوت آدرس بک‌اند، در ریشه فرانت فایل `.env` ایجاد کنید:

```env
VITE_API_URL=http://localhost:21547
```

در نبود این متغیر، همین آدرس به‌عنوان مقدار پیش‌فرض استفاده می‌شود.

## نکات فعلی و گام‌های بعدی

- APIها هنوز نیازمند `[Authorize]` نیستند. قبل از انتشار، سیاست دسترسی بر پایه عضو پروژه و نقش کاربر باید اضافه شود.
- ایجاد کلید وظیفه به شکل `PROJECTKEY-NUMBER` است. در درخواست‌های هم‌زمان زیاد، بهتر است این شمارنده با راهکار مقاوم در برابر رقابت جایگزین شود.
- Attachment تنها URL فایل را ذخیره می‌کند؛ برای آپلود فایل باید یک storage مانند local storage، MinIO یا Azure Blob اضافه شود.
- API مستقلی برای مدیریت اعضای پروژه، جلسات، یادآورها و فعالیت‌ها هنوز پیاده‌سازی نشده است.
- وضعیت‌های enum به صورت رشته در JSON پشتیبانی می‌شوند؛ برای مثال `"inprogress"` و `"done"`.

## بررسی انجام‌شده

فرانت‌اند با دستور زیر build شده است:

```powershell
npm run build
```

Build با موفقیت انجام شده است. در بک‌اند نیز لایه‌های Domain و Application کامپایل شده‌اند. اگر build کامل Web با خطای قفل DLL روبه‌رو شد، IIS Express یا اجرای فعال Visual Studio را متوقف کرده و دوباره build بگیرید.
